# v0.5.0 Private staging guide

## Configuration
Upgrade with the prior data folder intact. SmartConfiguration adds `private-preview: false` to config.yml, preserving previous values. Enable battle-preview and private-preview only in an isolated testing server. Keep foundation-only true. Use `battle.yml` in each floor and define one or more non-overlapping arenas with `mode: PRIVATE`; see BATTLE-GUIDE.md. Chunks for spawn/exit must already be loaded by the staging setup. `private/settings.yml`: enabled true, max-players 1..5, entry-cost TICKET, ticket-id dungeon_ticket, ticket-cost 1, cooldown-seconds 0. Global max-private-active defaults to 3; global max-private-players is a further cap. Ticket material and display-name come from ticket.yml. Existing serials remain accepted if the display material changes, because validity is based on PDC + ledger, not appearance. No Vault integration.

## Commands
Staff `/adg ticket give <online-player>` issues one unique ticket. `/adg ticket inspect <serial>` shows state; keep the serial in audit logs. Staff command `/adg ticket recover <serial> <session>` can refund an unresolved SPENT record if the session is not active, after verifying a hard-crash/system failure; never use it for a legitimate defeated party. CONSUMED tickets cannot be recovered. `/adg ticket claim <serial>` claims an undelivered issue/refund for its recorded owner. Permission `arunika.dungeon.admin` for issue/inspect/recover; `arunika.dungeon.private.test` for staging player functions (default op).

Player commands:
- `/adg private create queen_bee` (any configured and enabled Private floor)
- `/adg private invite <online-player>`, then invitee `/adg private accept` or `/adg private decline` within 60 seconds.
- Each player `/adg private ready`; `/adg private unready` before queue. Membership or leader changes reset readiness.
- `/adg private kick <online-player>`, `/adg private transfer <online-player>`, `/adg private leave`, `/adg private cancel`, `/adg private status`.
- Leader holds one ticket in main hand and runs `/adg private start`. Solo leader must also ready. Keep the same ticket in main hand while queued. Queue is FIFO per floor, skips floors without a free arena. Performance guard pauses dispatch. Ticket is not charged for waiting. Cancelling the queue resets readiness; a disconnect removes member or disbands leader's party. Queue expires after 10 minutes. Parties/invites/queue are deliberately transient across restart.

## Ticket transaction and recovery
One physical ticket per serial; default PAPER. The ledger records the current generation, session, payer, and pending recipient. States: AVAILABLE -> HELD -> SPENT -> CONSUMED. Refund from HELD/SPENT yields AVAILABLE at generation + 1 (prior item becomes inert). Ledger files use an atomic temp-file replacement with file force; one server process per data folder, local filesystem required. Never delete ticket records or restore an old ledger independently of inventory data: it can invalidate or resurrect tickets. Copy the entire data folder along with corresponding world/player saves for disaster recovery. Files accumulate with issued serials; no automatic pruning of spent records in this preview. Startup scans records to recover HELD; there are no per-player periodic disk tasks, but ticket state changes and inventory save are synchronous. Benchmark disk latency on staging.

- Failed arena validation before holding: no charge. Held ticket on failed launch: durable refund; invalid original may remain in inventory, but cannot be redeemed. Successful start commits before first battle tick. The leader's one physical item is removed after commit. Each claim is acknowledged after inventory delivery/save; if the server crashes between delivery and acknowledgment, a replay may yield a physical copy, but only one valid generation can be spent. This is redemption protection, not a claim of perfect physical item atomicity across independent player saves and ledger writes.
- Successful encounter, party elimination/leave, or time expiry: terminal CONSUMED. No refund. Recognized internal battle exceptions, missing tracked mob, staff abort, clean shutdown: refund. Future physical loot stage must audit deliberately triggered failures/refund abuse before production.
- HELD records are automatically refunded on restart before entering gameplay. SPENT with no final settlement can represent hard crash: no automatic refund, staff inspect logs and explicitly recover only verified system-failed sessions. Recovery logs serial; recipient can claim. File state writes failing during settlement lock new Private starts and report serial/session; repair storage and restart before further recovery. Hard power loss / filesystem corruption are not guaranteed recoverable.
- Pending refund delivery remains owner-bound until acknowledgment. Ticket may be traded after delivery; copies with same serial cannot both activate. Distinct valid serials do not normally stack. Unknown or malformed PDC cannot redeem. Creative/OP file manipulation is outside threat model.

## Staging verification required
1. Build with real Paper and dependency JARs. Confirm PDC read/write, item save/claim, and API compatibility on Java and Geyser Bedrock.
2. Test five-person party and simultaneous Shared on same floor, disabled floor, occupied arena, queue cancellation, partial teleport rejection, restart during HELD, server stop, boss complete and time expiry. Test full inventory and disconnect. Check all ledger states and player saves, including failure paths.
3. Confirm legacy plugins still own production commands/data; never activate preview in their active arenas. Existing basic arena protection only covers tracked participants/direct entities; MythicMobs custom summons, cross-plugin teleport and persistence of pending returns require final security audit. No loot yet.
